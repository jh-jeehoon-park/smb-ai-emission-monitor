## 6. 게스트 범위 — 원문 분석

`[원문 p.69]`는 "조회만 가능"이라며 **조작 여부만** 규정하고 범위를 말하지 않는다. 그러나 원문의 다른 곳이 **조작하지 않고 여러 사업장을 보는 이용자**를 반복해서 규정한다.

| # | 근거 | 출처 |
|---|---|---|
| 1 | 수요처 B2G — **지자체 환경관리 부서 · 산업단지 관리기관 · 환경공단**. 사업장을 운영하지 않고 **감독**한다 | `[원문 p.1]` |
| 2 | FR-31 다사업장 통합 모니터링 — "복수 사업장 원격 관리 수요", "SaaS플랫폼 기반 다중 사업장 통합 모니터링"(환경관리 대행업체) | `[원문 p.33]` |
| 3 | FR-32 단지 전체 통합 모니터링 — "입주 업체 통합 환경관리 수요", "단지 전체 실시간 모니터링 플랫폼 구축 수요"(산업단지관리공단) | `[원문 p.33·42]` |
| 4 | FR-33 관내 사업장 통합 관제 — "관내 비TMS사업장 통합 관제 시스템 구축 수요"(지자체 환경관리 부서) | `[원문 p.33]` |
| 5 | 확산 3단계 — "**단지 관리기관에 전체 입주 사업장 수질 현황 통합 모니터링 대시보드 제공**" | `[원문 p.85]` |

### 6.1 배제 논증

전 사업장을 **조작 없이** 보는 역할은 게스트밖에 없다.

- **관리자**는 "모든 기능 접근"이라 제어(FR-26)·설정까지 포함한다. 감독기관에 줄 수 없다.
- **운영자**는 "알람 확인"이라는 **조작**을 포함한다(§5.2에서 상태 전이로 확정).
- 게스트를 단일 사업장으로 좁히면 **FR-32·FR-33이 요구하는 "단지 전체"·"관내 전체" 통합 관제를 수행할 역할이 사라진다.**

### 6.2 반대 근거 탐색 결과

`docs/analysis/`·`docs/requirements/` 전수 검색에서 게스트를 단일 사업장으로 한정하는 서술은 **찾지 못했다**. "자사"·"소속 사업장"·"사업장주" 같은 표현이 권한 맥락에서 쓰인 곳이 없다.

## 8. 사업주는 어디에 속하는가

사용자가 "사업장의 **사업주**는 어느 권한인가"를 물었다. §5.1~5.3은 **담당자**를 다뤘고 사업주는 다루지 않았다.

### 8.1 원문에 사업주는 없다

원문이 사용자로 언급한 사람은 셋뿐이다.

| 대상 | 성격 | 출처 |
|---|---|---|
| 관리자 / 운영자 / 게스트 | **권한 정의** | `[원문 p.69]` |
| "현장 운영자" | 설계 방향 — 역할 정의 아님 | `[원문 p.50]` |
| 중소 폐수배출사업장 환경담당자 | 교육 대상 — 역할 정의 아님 | `[원문 p.42]` |

사업주 관련 언급은 B2B 직접 수요처 = "TMS 미부착 중소·영세 폐수배출사업장 약 6만 개소" `[원문 p.1]` 하나뿐이며, **구매 주체(조직)이지 사용자 역할이 아니다.**

### 8.2 판단: 관리자 × 자사 1개소

| 근거 | 출처 |
|---|---|
| 계약·구매 주체가 사업장 자체 | `[원문 p.1]` |
| 기대 효과가 **개소당**으로 산정된다 — 약품비 200~300만원, 사고 대응 2,500만원 | `[원문 p.40]` |
| 행정처분 리스크를 지는 주체 — 조업 정지 시 일 매출 100% 손실 | `[원문 p.19]` |

손익과 법적 책임이 사업주에게 귀속되므로 **조작 축은 관리자**로 본다.

### 8.3 이 질문이 드러낸 구조적 결함

사업주를 게스트로 두면 "조회만"에는 맞지만, §7.2가 **게스트를 "전 사업장 조회"로 확정**했다. 사업주는 자사 1개소만 봐야 한다.

**같은 역할에 서로 다른 데이터 범위가 필요하다.** 역할 하나로 조작 범위와 데이터 범위를 동시에 표현하려 한 것이 원인이다. §7.3에서 "역할별 조작 범위를 정한 것이지 계정별 데이터 범위를 정한 것이 아니다"라고 각주로 넘겼는데, 사업주를 넣으면 넘길 수 없다.

**해소: 두 축으로 나눈다.** 정의는 [`docs/specs/README.md`](../specs/README.md) §4.4에 있다.

| 실제 사용자 | 조작 | 범위 |
|---|---|---|
| 사업주 | 관리자 | 자사 1개소 |
| 사업장 담당자 | 운영자 | 자사 1개소 |
| 환경관리 대행업체 | 운영자 | 위탁 복수 |
| 지자체·단지 관리기관 | 게스트 | 전체 |

§7.2의 "전 사업장"은 **범위 축의 값**이지 게스트 역할의 정의가 아니다.

## 9. 정정 — 운영자에게 운영 최적화를 연다

### 9.1 무엇이 틀렸나

§7.1은 운영자 화면을 **관측 6개**로 정하고 운영 최적화(SCR-AD-006)를 "처방이지 모니터링이 아니다"라며 제외했다. **`[원문 p.69]`만 보고 내린 결정이다.**

### 9.2 놓친 근거

`[원문 p.50]`이 Application Layer를 **"현장 운영자 중심 설계"** 로 규정하면서, 같은 층의 **운영 의사결정 지원 항목**에 이것들을 넣는다.

- 약품 주입량 권장
- 설비 운전 조건 제안
- 알람 및 이벤트 관리

즉 **원문은 현장 운영자가 운영 최적화를 쓰는 것을 전제한다.** p.69의 좁은 문구와 어긋나며, 이 충돌을 `[INC-94]`로 등록했다.

여기에 운영 인력 **개소당 0.5~1명** `[원문 발표 p.49]`이 겹친다. 사업장에 한 명 이하인데 권한을 쪼갤 수 없다. 그 한 명에게 모니터링만 주면 **약품비 20~30% 절감** `[원문 p.27·31]`이라는 시스템의 핵심 가치를 정작 그 사람이 못 쓴다.

### 9.3 정정된 운영자 범위

**관측 6개 + 운영 최적화 = 7개.**

| 화면 | 열림 | 근거 |
|---|---|---|
| SCR-AD-001~005 | ○ | 모니터링 `[원문 p.69]` |
| SCR-AD-006 운영 최적화 | **○ (정정)** | 운영 의사결정 지원 `[원문 p.50]` `[INC-94]` |
| SCR-AD-007 알람 이력 | ○ (R·U) | 알람 확인 `[원문 p.69]` |
| SCR-AD-008 리포트 | ✕ | 내보내기가 주 기능. 조작 축 밖 |

게스트는 **7개 전부 조회 가능하되 조작 없음**(알람도 R만). 리포트는 관리자만.

### 9.4 남는 것

`[INC-94]`는 **해소된 것이 아니라 등록된 것이다.** p.69의 "모니터링"이 운영 의사결정 지원을 포함하는지는 발주처 확인이 필요하다. 프로토타입은 p.50과 인력 구조를 근거로 포함하는 쪽을 택했다.

## 10. 원문 직접 재확인 (2026-08-13)

### 10.1 왜 다시 봤나

§5~§9의 판단은 전부 `docs/analysis/`·`docs/requirements/`(파생 문서)를 근거로 했다. 사용자가 **"문서 전체를 제대로 분석하지 못한 상태"** 라고 지적해 원본 PDF 2건을 직접 읽었다.

- 사업계획서 121p · 발표자료 52p **전수 키워드 스캔**(관리자·운영자·게스트·권한·RBAC·사용자·담당자·사업주·계정 등)
- 역할 관련 페이지는 텍스트 전문 확인

### 10.2 확인 결과

| 항목 | 결과 |
|---|---|
| p.69 접근제어 | **정확히 6줄이 전부.** 파생 문서 기록과 일치. 추가 서술 없음 |
| 사용자 기능 목록 | p.31~32 "클라우드 기반 사용자 기능" 6종 — **역할 배정 없음.** 약품 주입량 최적화 제안 포함 |
| Application Layer | p.49~50 운영 의사결정 지원 3종 + "현장 운영자 중심 설계" |
| 발표자료 | 52p 전수 스캔에서 역할 언급은 p.20 "최종 사용자" **한 곳뿐** |
| 사업주 | 사용자 역할로 **없음** — §8 판단 유지 |

### 10.3 놓쳤던 것

현장 운영자가 누구인지 원문이 구체적으로 서술하는데, 그 내용이 `functional-requirements.md` §3(사용자 및 권한)이 아니라 `project-overview.md` **추진 배경**에 있어 역할 판단 때 참조되지 않았다. SWOT 약점(p.83)은 파생 문서 어디에도 없었다.

전문을 [`functional-requirements.md` §3.3.1](../requirements/functional-requirements.md)로 옮겼고, 화면 설계 원칙으로 [`specs/README.md` §4.4](../specs/README.md)에 반영했다.

### 10.4 §9 판단은 유지된다 — 근거가 두터워졌다

운영자에게 운영 최적화를 여는 판단의 근거가 p.50 하나에서 넷으로 늘었다.

1. 사용자 기능 목록(p.31~32)이 **약품 주입량 최적화 제안을 포함하면서 역할을 나누지 않는다**
2. 그 기능군이 **"현장 운영자 중심 설계"** 로 규정된다(p.50)
3. 위험 대응이 **"자동 의사결정 가이드"·"알림 기반 단순화된 운영 방식"** 을 대응책으로 든다(p.94)
4. 운영 인력이 개소당 0.5~1명이다(발표 p.49)

`INC-94`의 B측 근거도 이에 맞춰 보강했다. **판정이 바뀐 것이 아니라 근거가 두터워진 것이다.**
