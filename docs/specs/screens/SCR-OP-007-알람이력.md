### 2.1 권한

| 관리자 | 운영자 | 게스트 |
|---|---|---|
| R·U | R·U | R |

`[원문 p.69]` 운영자에게 "알람 확인" 권한이 있다. **'확인'이 조회인지 상태 전이까지인지 원문이 답하지 않는다** `[TBD]`.

사이드바 메뉴에 **미확인 건수 배지**가 붙는다 `[설계: 다른 화면에 있어도 밀린 알람이 눈에 들어와야 한다]`. **배지 숫자도 범위를 따른다** — 관리자는 자사 미확인만 센다.

**관리자는 자사 1개소만 본다** `[회의 2026-08-13]` — **구현됨**. 라우트 가드가 URL에 `?site=자사&scope=site`를 박고, 주소를 직접 고쳐도 되돌린다. 범위를 URL에 두는 이유는 서버가 역할을 모르기 때문이다([README §4.4](../README.md)).

관리자에게는 `전 사업장 / 선택 사업장` 범위 세그먼트를 숨긴다 — 고를 것이 없다. **상단 지표 타일도 같은 범위에서 센다** `[설계: 목록과 타일이 각자 범위를 계산하던 탓에 세그먼트를 바꿔도 타일 숫자는 전 사업장 그대로였다. 판정을 한 곳으로 모았다]`. 우선순위·상태 필터는 타일에 **일부러** 반영하지 않는다 — 걸러낸 건도 세션 집계에는 남아야 한다.

## 4. 요구 데이터

### 4.1 알람 (`Alarm`)

| 데이터 | 타입 | 근거 |
|---|---|---|
| `id` `siteId` `siteName` | string | `[설계]` 식별·소속 |
| `priority` | `urgent`\|`caution`\|`info` | 긴급/주의/정보 3종 `[원문 p.32]` |
| `condition` | `anomaly`\|`pollutionSurge`\|`qualityShift`\|`equipment` | 이상 탐지/오염도 급변/수질 변화 이상/설비 이상 4종 `[원문 p.32]` |
| `state` | `open`\|`acknowledged`\|`resolved` | 미확인/확인/조치 완료 `[설계]` — 원문에 상태 정의 없음 |
| `title` `detail` | string | `[설계]` 알람 내용 |
| `raisedAtIso` | ISO8601 | 발생 시각 (KST 표기, **E5**) |

정렬은 **발생 시각 내림차순** `[설계: 이력 화면의 기본 관심은 방금 무슨 일이 있었는가다]`.

#### 비방류 중 발생 표시

수질 계열 알람(`pollutionSurge`·`qualityShift`)이 **방류하지 않는 동안** 올라왔으면 조건 라벨 아래에 `비방류 중 발생`을 적는다.

| 항목 | 값 |
|---|---|
| 근거 | `[데이터셋 docs/datasets/Non_TMS_sites/04_사업장_유량,전력,전류 가동시간]` — 진유원 방류 88.3%, 272일 중 15일은 0시간 |
| 왜 | **방류하지 않는 시간의 수질값은 배출 수질이 아니다.** `TOC 급변 — 배출기준 초과 예상` 같은 제목이 비방류 중에 붙으면 초과가 임박한 것처럼 읽힌다 `[설계]` |
| 대상 | 수질 계열 **2종만**. `anomaly`·`equipment`는 방류와 무관하게 공정에서 일어난다 `[설계]` |

**필드로 저장하지 않고 `raisedAtIso`에서 파생한다** `[설계: 저장하면 시나리오와 어긋날 수 있지만 파생은 어긋날 수 없다]`. 구현은 [`entities/alarm/lib/discharge-context.ts`](../../../src/entities/alarm/lib/discharge-context.ts)이며 시간축은 [`shared/lib/timeline.ts`](../../../src/shared/lib/timeline.ts)의 `isDischargingAt`을 쓴다.

**통신 두절 구간은 표시하지 않는다.** 그 시간의 방류 여부는 `null`(모름)이고, 모르는 것을 "방류 안 했다"로 바꿔 적으면 없는 사실을 주장하게 된다(**E4**).

#### 확인 상태는 셸이 공유한다

확인·조치 결과는 [`AlarmStateProvider`](../../../src/features/alarm-ack/model/alarm-state-context.tsx)가 셸에서 들고, **헤더 알림·사이드바 배지·통합 관제·자사 현황·이 화면이 같은 값을 본다** `[설계]`.

예전에는 이 화면만 지역 `useState`를 들고 나머지는 정적 fixture를 읽었다 — 여기서 확인 처리를 해도 사이드바 배지가 그대로였다. **헤더에 알림을 두면서 그 어긋남이 세 곳으로 늘어나므로** 상태를 한 곳으로 올렸다.

집계 함수도 배열을 받는 순수 함수로 바꿨다(`countOpen`·`openAlarms`). 모듈 상수를 직접 읽으면 덮어쓴 상태를 볼 수 없다.

**서버가 없어 저장되지 않는다.** 새로고침하면 fixture 상태로 돌아간다 — 시연용 상태 전이지 실제 처리 이력이 아니다(기존과 같다).

**건수 집계와 필터는 나누지 않는다** `[사용자 결정 2026-08-18]`. 목록 표시까지만 한다 — 행 수가 바뀌지 않아 하이드레이션 위험이 없고, 원문에 없는 법정 초과 판정을 지어내지 않는다.

## 5. 상호작용

| 조작 | 동작 | 결과 |
|---|---|---|
| 범위·우선순위·상태 세그먼트 | 목록 필터 | `?scope=` `?prio=` `?state=` 갱신 |
| `확인 처리` | `open → acknowledged` | 상태 칩 갱신 · 요약 타일 즉시 반영 · 되돌리기 버튼 노출 |
| `조치 완료 처리` | `acknowledged → resolved` | 위와 같음 |
| `변경 N건 되돌리기` | 전체 원복 | fixture 상태로 복귀 |

상태는 **단방향으로만** 흐른다 `[설계: 미확인 → 확인 → 조치 완료. 되돌리는 동선을 개별 행에 두지 않는다]`.

버튼을 **동사로** 적는다 `[설계: 같은 화면의 상태 필터가 '확인'이라 명사를 쓰면 무엇을 거르고 무엇을 실행하는지 구분되지 않는다]`.

| xlsx 열 | 값 |
|---|---|
| SUBMIT | 확인 처리 / 조치 완료 처리 |
| CANCEL | 변경 되돌리기 |
| After Action | 상태 칩·요약 타일 즉시 갱신. 화면 이동 없음. **저장되지 않는다** |

## 7. 설계 근거

**상태 전이가 브라우저 메모리에만 남는다** `[설계: 서버가 없어 저장할 곳이 없다]`. 화면에 그 사실을 적고 **되돌리기 버튼**을 둔다 — 시연 중 원상복구가 필요하다.

**요약 타일을 둔 이유** `[설계: 목록만 바뀌면 처리한 티가 나지 않는다. 확인·조치를 누르면 숫자가 바로 움직여야 한다]`. 화면에 큰 수치가 하나도 없어 훑을 기준점이 없던 문제도 함께 해소한다.

**등급 ↔ 우선순위를 매핑하지 않았다** `[INC-02: 알람 우선순위(긴급/주의/정보)와 상태 등급이 "별개 축인지 같은 축인지 원문에 설명이 없다"]` `[설계: 임의로 이으면 두 축이 하나인 것처럼 읽힌다]`.

**발송 채널 설정 UI를 만들지 않았다** `[설계: 발송 주체가 서버다(REQ-CO-003). 채널 설정만 만들면 동작하지 않는 화면이 된다]`. 채널 자체는 원문에 있으나 `[원문 p.31·68]` SMS·이메일·모바일 푸시 / `[원문 p.88]` SMS·앱 푸시 / `[원문 발표 p.15]` SMS·시스템으로 **4가지 조합이 등장한다** `[INC-86]`. 임계값 수치도 원문에 없다 `[TBD-01]`.

### 8.1 원문 알람 목록 예시와의 대조 `[원문 발표 p.20 그림]`

| 열 | 원문 예시 | 우리 목록 | 판단 |
|---|---|---|---|
| **등급** | `경고` · `주의` | **없다** | 어긋난다 |
| 구분 | `TN 기준 초과 예측` · `펌프 진동 이상` · `유량 급변 감지` | 조건 4종(이상 탐지·오염도 급변·수질 변화 이상·설비 이상) | 원문 쪽이 구체적이다 |
