## 4. 요구 데이터

### 4.1 검증 원천 — **둘이며 성격이 다르다**

| 원천 | 주기 | 항목 | 대상 | 근거 |
|---|---|---|---|---|
| 위탁 실험실 수분석 | **월 2회** | COD·TOC·TN·TP·SS | 전 사업장 | `[원문 p.38]` "월 2회 수분석 대비 AI예측값 비교" |
| TN/TP 분석기 | 연속 측정 | TN·TP | **대표 실증사업장 1개소** | `[원문 발표 p.17]` "대표 실증사업장 1개소 TN/TP 분석기 설치 기반 AI 추정 결과 비교 검증" |

> **월 2회는 법정 주기가 아니다.** 법정 자가측정은 월 1회~분기 1회다 `[공정자료 p.13]`. 둘을 같은 것으로 적으면 규제 요건을 잘못 전한다.

### 4.2 회차 (`AnalysisRound`)

형식은 실증 성적서를 그대로 따른다 `[데이터셋 Non_TMS_sites/05]`.

| 데이터 | 타입 | 근거 |
|---|---|---|
| 발급번호 | string | 성적서 체계(`YYYYMMDD-nnn`) |
| 접수일 · 시험기간 | ISO8601 · string | 성적서 항목 |
| 분석 기관 | string | 위탁 분석 기관 |
| 시료 | `AnalysisSample[]` | **9:45부터 매시 8건** — 실증 성적서가 그랬다 |
| 시료별 접수번호 | string | 성적서가 시료마다 매긴다 |

**값의 크기는 시연 계열에 맞춘다** `[설계: 성적서 실측(TOC 6.1·TN 7.44·TP 0.435)을 그대로 쓰면 우리 AI 추정 계열(TOC 25~39)과 자릿수가 달라 오차가 500%로 나온다. 검증 화면이 보여야 할 것은 대조 방법이지 두 시연 값의 우연한 차이가 아니다]`. 성적서에서 가져온 것은 **형식**이다.

**AI 추정값은 회차마다 다르며 그 회차 실측을 따라간다** `[설계: 실제 시스템은 운영 이력 저장소에서 그 시각의 추정값을 읽는다(REQ-AD-030 미구현). 예측 화면의 현재값 하나를 열두 회차에 붙이면 상수 예측이라 항목별 R²가 정의되지 않고, 실측과 무관한 난수로 뽑으면 상관이 없어 R²가 음수로 나온다 — 둘 다 모델 성능이 아니라 생성 방식의 결과다]`. **오차 폭은 시연값이며 성능 목표가 아니다** — 현재 시연값의 R²는 0.26~0.69로 원문 목표 `R²>0.75` `[원문 p.30]` **아래**이며, 목표를 만족하도록 맞추지 않았다.

### 4.3 대조표 (`ComparisonRow`)

| 항목 | AI 추정 | 비고 |
|---|---|---|
| TOC · TN · TP | ✓ | 대조 가능 |
| **SS** | ✗ | **계측·추정 대상이 아니다** — 탁도는 물리 지표일 뿐 SS가 아니다 `[공정자료 p.5·19]` |
| COD | ✗ | TOC로 대체되어 **현재 폐지** `[공정자료 p.12·16]` |

**SS·COD 행을 빼지 않는다** `[설계: 법정 방류기준 점검 5항목(TOC·SS·T-N·T-P·pH) 중 우리가 못 보는 항목이 있다는 사실이 화면에서 사라진다]`. 대신 그 자리에 **왜 없는지**를 적는다.

### 4.4 검증 지표 (`ValidationMetrics`)

| 데이터 | 타입 | 근거 |
|---|---|---|
| R² | number \| null | `[원문 p.38]` "오염도 추정 정확도 검증(R²·MAE 기반)" |
| MAE | number \| null | 동일 |
| 표본 수 | number | `[설계]` 값과 함께 다녀야 신뢰도를 읽을 수 있다(**E3**) |

**표본이 2개 미만이면 `null`이다** — 한 점으로 결정계수를 정의할 수 없는데 `1`이나 `0`을 내면 검증된 성능처럼 읽힌다.

지표는 **항목별로, 회차를 가로질러** 계산한다. 세 항목을 한 데 모으면 안 된다 `[설계: TOC 25 · TN 16 · TP 1.5로 크기가 달라 항목 간 차이가 총제곱합을 채운다. 모아서 계산했을 때 R²가 0.99로 나왔는데 이는 추정 정확도가 아니라 항목 간 크기 차이였다]`.

## 7. 설계 근거

**검증 원천을 둘로 나눠 보인다** `[설계: 원문이 서로 다른 두 방식을 규정하는데(월 2회 위탁 분석 / 대표 1개소 분석기) 한 이름으로 묶으면 "모든 사업장에 분석기가 있다"로 읽힌다]`.

**지표를 항목별로 낸다** `[설계: 모아서 계산하면 항목 간 크기 차이가 R²를 부풀린다. 실제로 0.99가 나왔고, 그것은 추정 정확도가 아니었다]`.

**자가측정과의 법적 관계를 화면에 적는다** `[설계: TMS는 측정되는 항목만 자가측정을 대체하고, BOD·중금속 등은 의무가 유지된다(공정자료 p.13·14). 우리 대상은 비TMS라 대체 관계 자체가 성립하지 않는다. 이 문장이 없으면 "AI가 있으니 분석을 줄여도 된다"로 읽힌다]`.

## 8. 미정·제약

| 항목 | 표기 | 확정 필요 시점 |
|---|---|---|
| 대표 실증사업장 | **시연 선택** | 원문은 "1개소"라고만 한다 `[원문 발표 p.17]` — 확정 시 `ANALYZER_SITE_ID` 하나만 교체 |
| 회차 시각의 AI 추정 이력 | REQ-AD-030 미구현 | 운영 이력 저장소가 생길 때 — 지금은 시연값을 생성한다 |
| 시연 데이터의 R² | 0.26~0.69 | 원문 목표 `R²>0.75` `[원문 p.30]`와 **무관하다**. 생성 방식의 부산물이지 측정된 성능이 아니다 |
| 분석기 연계 검증의 화면 형태 | 안내 문단까지만 | 분석기 데이터 형식 확인 후 — 연속 대조 차트가 필요할 수 있다 |
| 수분석 항목 확장 | 5종 | 중금속·특정수질유해물질도 자가측정 대상이다 `[공정자료 p.14]`. 계측·추정 대상이 아니라 지금은 싣지 않는다 |

### 8.2 원문 검증 절차와의 대조 `[원문 발표 p.27 그림]`

발표자료 p.27이 실증 검증을 **7단계**로 규정한다 — 수집 → 전처리 → AI 학습 → **TN/TP 실측 분석기 연계 검증** → **공인 수분석 결과 비교 검증** → 실증 운영 → 재학습.

| 항목 | 원문 | 우리 화면 | 판단 |
|---|---|---|---|
| 검증 원천 | 분석기 연계 · 공인 수분석 **두 단계** | 두 원천을 나눠 싣는다 | 같다 |
| **지표** | **R², MAE/RMSE** | R² · MAE | **RMSE가 빠져 있다.** MAE와 함께 내면 큰 오차의 영향이 드러난다 — 지금 데이터로 바로 낼 수 있다 |

> `발표 p.27`은 한 줄에 `R², RMSE/MAE, F1 Score`로 묶어 적지만, **`발표 p.26`이 둘을 나눈다** — 수분석 비교 검증은 `R², MAE/RMSE`이고 **F1 Score는 이상 탐지 정확도 지표**(≥90%)다. 검증 화면에 F1을 넣지 않는다.
| 용어 | **공인** 수분석 | 위탁 실험실 수분석 | 원문 용어가 `공인`이다. 다음 갱신에서 맞춘다 |

**RMSE는 지금 데이터로 바로 낼 수 있다.** F1 Score는 무엇을 양성으로 볼지가 정해져야 한다 `[TBD-17]`.
