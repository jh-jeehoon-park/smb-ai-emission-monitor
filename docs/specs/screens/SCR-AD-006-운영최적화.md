### 2.1 권한

| 관리자 | 운영자 | 게스트 |
|---|---|---|
| R | R | R |

`[원문 p.50]`이 Application Layer를 **"현장 운영자 중심 설계"** 로 규정하면서 같은 층의 운영 의사결정 지원 항목에 **약품 주입량 권장·설비 운전 조건 제안**을 넣는다. 운영자에게 연다.

**p.69의 "운영자 = 모니터링, 알람 확인"과 어긋난다** `[INC-94]`. 운영 인력이 개소당 0.5~1명 `[원문 발표 p.49]`이라 약품을 조정할 사람이 그 한 명뿐이고, 닫으면 약품비 20~30% 절감 `[원문 p.27·31]`을 그 사람이 못 쓴다 — 그래서 여는 쪽을 택했다. 경위는 [명확화 기록 §9](../../logs-clarifications/2026-08-13_역할별-화면-권한.md).

게스트는 조회만 — 권장값은 보되 적용 동선이 없다(현재 화면에 적용 기능 자체가 없다).

## 4. 요구 데이터

### 4.1 성능 목표 (전부 원문 수치)

| 지표 | 값 | 근거 |
|---|---|---|
| 약품비 절감 | 20~30% | `[원문 p.27·31]` 현재 검증 수준 |
| 에너지 절감 | ≥ 10% | `[원문 p.27·64]` |
| 총 운영비 절감 | ≥ 12% | `[원문 p.27·31·64]` |
| 산출 모델 | XMARL-PPO (다중 에이전트 강화학습) | `[원문 p.64·66]` Decision Optimization Layer |
| 모델 입력 | 수질 상태(LSTM 예측 포함) · 설비 상태(전력·전류·운전율) · 운영 변수(약품 주입량·폭기량) | `[원문 p.66·67]` |

> **설비 수명 증가 목표는 쓰지 않는다** `[INC-18: 같은 페이지에서 ≥15%와 ≥10%로 갈린다]`.

### 4.2 약품 주입량 (`DosingAdvice`)

| 데이터 | 타입 | 단위 | 근거 |
|---|---|---|---|
| `currentDose` | number | L/h | **단위·범위가 원문에 없다** `[PROVISIONAL, TBD-31]` |
| `recommendedDose` | number | L/h | 최적 주입량 제안 `[원문 p.32·67]` |
| `savingRate` | number | % | 20~30% 범위 안 `[원문 p.27·31]` |
| `basis[]` | string[] | — | **E3** 권장 근거 |

`[TBD-31 관련]` — data-dictionary §5.1이 "약품 주입량 — 원문 없음(형식·단위)", "최적 약품 투입량 권장값 — 원문 없음(범위)"로 기록한 항목이다. 계측 사양 `[원문 p.55]`에 없고 AI 입력 운영 데이터로만 언급된다.

### 4.3 설비 운전 조건 (`OperatingAdvice[]`)

| 데이터 | 타입 | 단위 | 근거 |
|---|---|---|---|
| `parameter` | string | — | 폭기량 · 펌프 속도 · 주입 속도 `[원문 p.67]` |
| `target` | string | — | 조정 대상 설비 |
| `deltaPercent` | number | % | **현재 대비 상대 변화** |
| `reason` | string | — | **E3** 조정 이유 |

**절대 단위(폭기량 m³/min, 회전수 rpm)가 원문에 없다** `[TBD]`. 값을 지어내지 않고 상대 변화만 낸다 `[설계: 방향과 크기만으로도 운전자가 판단할 수 있고, 단위가 확정되면 절대값을 붙이면 된다]`.

### 4.4 에너지 효율 (`EnergyAdvice`)

| 데이터 | 타입 | 단위 | 근거 |
|---|---|---|---|
| `current` | number \| null | kWh/m³ | `[파생: 평균전력(kW) × 24 ÷ 평균유량(m³/day)]` · 단위 `[원문 p.67]` |
| `target` | number \| null | kWh/m³ | `[파생: current × (1 − 10%)]` · 절감 목표 `[원문 p.27·64]` |
| `savingRate` | number | % | 10 `[원문 p.27·64]` |

**이 화면에서 유일하게 fixture가 아닌 값이다.** 계측 전력·유량에서 실제로 계산한다([`energy.ts`](../../../src/entities/measurement/lib/energy.ts)). 두 값 모두 순간값이라 조회 창 길이와 무관하게 같은 결과가 나온다.

결측은 빼고 계산한다 — **전력만 결측인 구간을 0으로 채우면 효율이 2.0에서 1.0으로 절반이나 좋아 보인다**(테스트로 고정, **E4**).

### 4.5 예상 비용 절감액

| 데이터 | 값 | 근거 |
|---|---|---|
| 연 약품비 기준 | 10,000,000원 | `[원문 p.32·34]` **예시 금액** |
| 연 전력비 기준 | 5,000,000원 | `[원문 p.32·34]` **예시 금액** |
| 절감액 | `[파생: 기준 금액 × 절감률]` | |

**사업장별 약품 단가·계약 전력이 원문에 없어 금액을 사업장마다 만들지 않았다** `[설계]`. 원문이 든 예시 금액에 절감률을 적용하고, **이 사업장의 실제 비용이 아님을 화면에 적는다.**

## 7. 설계 근거

**이 화면은 처방이다** `[설계: 다른 화면이 전부 관측(무슨 일이 있었나)인데 처방(무엇을 할까)이 비어 있었다. 사업의 핵심 가치가 "AI가 제안해 비용을 줄인다"이다]`.

**현재와 권장을 같은 축의 막대로 겹친다** `[설계: 숫자만으로는 차이가 눈에 들어오지 않는다]`.

**운전 조건은 중앙 기준 양방향 막대다** `[설계: 부호만 적으면 어느 쪽이 더 큰 조정인지 비교되지 않는다]`.

**에너지 효율만 실제로 계산한다** `[설계: 계측 전력·유량이 이미 있으므로 지어낼 이유가 없다. 계산할 수 있는 것을 fixture로 만들면 그만큼 검증할 수 없어진다]`. 계산은 measurement의 몫, 권장값은 optimization의 몫이라 **두 도메인을 잇는 일은 위젯이 한다**(FSD §8 — slice끼리 참조하지 않는다).

**금액을 사업장별로 만들지 않는다** `[설계: 단가가 없는데 금액을 내면 확정된 값처럼 읽힌다. 원문 예시임을 밝히는 편이 정직하다]`.
