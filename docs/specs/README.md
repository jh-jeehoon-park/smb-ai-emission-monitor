## 2. 이 디렉터리가 답하는 질문

> **"이 화면의 이 숫자는 어디서 왔는가?"**

지금까지 그 답은 세 군데에 흩어져 있었다 — 데이터 명세, 디자인시스템 문서, 코드 주석. 화면이 8개가 되고 역할별 화면이 남은 상태에서는 어떤 값이 원문 근거이고 어떤 값이 우리 결정인지 한눈에 확인할 수 없다.

`docs/specs/`는 그 답을 한곳에 모은다. **원문(사업계획서·발표자료)에 있는 값과 우리가 정한 값을 표기로 구분**하는 것이 이 디렉터리의 존재 이유다.

### 다른 디렉터리와의 경계

| 어디 | 무엇을 담는가 | 여기와의 관계 |
|---|---|---|
| [`docs/analysis/`](../analysis/) | 원문에 **있는 것**을 정리 | 근거의 출처. 여기서 인용한다 |
| [`docs/requirements/`](../requirements/) | 원문이 요구하는 기능(FR)과 **정하지 않은 것**(TBD·INC) | 근거의 출처. 여기서 인용한다 |
| **`docs/specs/`** | **화면·요구사항·데이터를 근거와 함께 확정** | 이 디렉터리 |
| [`design-system/`](../../design-system/) | 색·타이포·지도 등 **시각** 결정과 그 근거 | 중복하지 않고 링크로 가리킨다 |

시각 결정을 여기에 복제하지 않는다. 색 팔레트가 왜 그 값인지는 [`design-system/smb-ai-emission-monitor/pages/dashboard.md`](../../design-system/smb-ai-emission-monitor/pages/dashboard.md)가 검증기 결과와 함께 갖고 있다.

## 3. 근거 표기 규약 — 이 디렉터리의 핵심 규칙

**모든 수치·항목·라벨에 아래 표기 중 하나가 반드시 붙는다.** 표기가 없는 값은 이 디렉터리의 문서에 쓸 수 없다.

| 표기 | 뜻 | 예 |
|---|---|---|
| `[원문 p.32]` | 사업계획서·발표자료에 그대로 있는 값 | 약품비 절감 20~30% `[원문 p.27·31]` |
| `[파생: 식]` | 원문 값이나 계측에서 계산한 값 | 에너지 효율 `[파생: 평균전력×24÷평균유량]` |
| `[PROVISIONAL]` | 원문에 없어 임시로 정한 값 | 약품 주입량 단위 `L/h` `[PROVISIONAL, TBD-31]` |
| `[TBD-nn]` | 원문이 정하지 않음 — 확인 필요 | MPI 산정식 `[TBD-22]` |
| `[INC-nn]` | 원문끼리 어긋남 — 채택안과 이유를 함께 | 상태 등급 4단계 `[INC-01·03·04]` |
| `[설계]` | 원문에 없는 우리 결정 — **이유를 함께 적는다** | 시도 클릭 확대 `[설계: 10개소 중 7개소가 클릭 영역 침범]` |
| `[회의 YYYY-MM-DD]` | **사업신청서 밖에서 정해진 것** | 운영자 = 전 사업장 통합 관제 `[회의 2026-08-13]` |
| `[공정자료 p.nn]` | **주관사 작성 공정 설명 자료** — 원문이 아니다 | 응집제 투입 = 1차 침전 앞 `[공정자료 p.4·6]` |
| `[데이터셋 경로]` | **HSK 제공 실측 샘플** — 원문이 아니다 | 탁도 기준치 상한 30 `[데이터셋 docs/datasets/Non_TMS_sites/02_사업장_이상데이터]` |
| `[원문 발표 p.nn]` | 발표자료. **`[발표 p.nn]`으로 줄이지 않는다** | 등급 4단계 `[원문 발표 p.15·18]` |
| `[사용자 지시 YYYY-MM-DD]` | 사용자가 지시한 작업 방향 | 헤더 시계 서식 `[사용자 지시 2026-08-20]` |
| `[사용자 결정 YYYY-MM-DD]` | 선택지를 사용자가 고른 것 | xlsx 산출법 `[사용자 결정 2026-08-20]` |
| `[사용자 확인 YYYY-MM-DD]` | 사용자가 사실로 확인해 준 것 | 수질 센서 8종 `[사용자 확인 2026-08-19]` |
| `[사용자 요청 YYYY-MM-DD]` | 사용자가 요청한 화면·기능 | RUL 예측 그래프 `[사용자 요청 2026-08-19]` |
| `[사용자 지적 YYYY-MM-DD]` | 사용자가 잡아 준 결함 | 리본 가독성 `[사용자 지적 2026-08-18]` |

위 14종이 전부다. **`[사용자 …]` 5종은 실사용 43회인데 이 표에 없었다** — `[회의]`와 같은 뿌리(사업신청서 밖에서 정해진 것)이며, 사용자 요청도 **왜 요청됐는지**를 함께 적어야 근거가 된다. "사용자가 원해서"는 근거가 아니다.

**뿌리가 다른 표기가 셋이다** — `[회의]`·`[공정자료]`·`[데이터셋]`. 나머지는 전부 원문(사업계획서·발표자료)을 뿌리로 하지만 이 셋은 그렇지 않다. 섞으면 "원문이 그렇게 말했다"와 "다른 자료가 그렇게 말했다"를 구분할 수 없고, 근거의 강도를 알 수 없게 된다.

| 표기 | 무엇인가 | 주의 |
|---|---|---|
| `[공정자료]` | [`docs/applications/폐수처리 공정 및 데이터 이해.pdf`](../applications/) — 주관사 개발본부 작성 | **매일유업 TMS 설치 사업장 기준**이다. 우리 대상(비TMS 소규모)과 계측 밀도가 다르다 |
| `[데이터셋]` | [`docs/datasets/`](../datasets/) — HSK 제공 실측 샘플 | TMS 사업장(매일유업)과 비TMS(진유원)가 나뉘어 있다. **어느 쪽인지 밝히지 않으면 오독된다** |

`[데이터셋]`은 경로가 실제로 있는지 `verify:docs` 검사 11이 확인한다 — 없는 파일을 근거로 적는 것을 막는다.

### 3.1 원문 밖 설계를 적는 형식

**원문에 없는 것이어도 관리자에게 필요하면 만든다** `[사용자 지시 2026-08-13]`. 대신 그 `[설계]`에는 **세 요소를 함께** 적는다. 하나라도 빠지면 "왜 이 값인가"에 답할 수 없다.

| 요소 | 내용 |
|---|---|
| **왜 필요한가** | 어떤 질문·부담에 답하는가. 가능하면 원문의 *문제 서술*을 인용한다 |
| **원문에 왜 없는가** | 누락인지, 다른 산출물인지, 미확정인지. 해당 `[TBD-nn]`·`[INC-nn]` |
| **확정되면 무엇을 바꾸는가** | 교체 지점(파일·상수). 되돌릴 수 있게 |

예 — `[설계: 조치 문구는 원문에 없다(FR-22는 "대응 가이드 제공"까지만). 겸직 70%·경험 기반 추정(원문 p.19·22)이라는 문제 서술에 답하려면 문구가 필요하다. 문구는 provisional에 모아 두고, 업종별 운영 가이드(2차년도 산출물 원문 p.87)가 나오면 교체한다]`

**그래도 지어내지 않는 것이 둘 있다.**

| 항목 | 이유 |
|---|---|
| 배출허용기준 등 **법정 판정값** | 법령이 원천이다. 우리가 정하면 그냥 틀린 값이 된다. 원문에 있는 것은 TP 2·4 mg/L와 하천 BOD 목표뿐이다 `[원문 p.18·19]` |
| 설비 제어의 **안전 인터록** | 없으면 위험한 동작을 만든다. 시연이라도 마찬가지다 |

### 3.2 "원문에 없다"고 적기 전에 — **이미지를 먼저 판독한다**

**같은 실수를 두 번 했다.** 무단방류 의심 탐지와 업종별 수질항목 조합을 각각 "원문에 근거가 없다"고 적었는데, 둘 다 **발표자료 그림 안에 있었다.** PDF 텍스트 추출은 **그림에 박힌 글자를 읽지 못한다.**

| 규칙 | 내용 |
|---|---|
| **판독 선행** | `[TBD-nn]`을 새로 만들거나 "원문에 없다"를 근거로 쓰기 전에, 그 주제 쪽의 **이미지를 열어 본다** |
| **대장에 남긴다** | 판독한 쪽은 [`source-inconsistencies.md` §5.4 판독 대장](../requirements/source-inconsistencies.md)에 결과와 함께 기록한다. **`미판독`이 남아 있는 쪽을 근거로 부재를 주장하지 않는다** |
| **판독 한계를 안다** | 벡터로 그려진 도형·글자는 텍스트로도 이미지로도 추출되지 않는다. `완료`가 "그 쪽을 전부 봤다"는 뜻은 아니다 |
| **AI 생성 그림을 구분한다** | 사업계획서 p.65·69처럼 글자가 뭉개진 그림이 있다. **수치·문구를 인용하지 말고 구조만 읽는다** |

판독 대장의 모든 행이 상태를 갖는지는 `verify:docs` **검사 12**가 확인한다.

**원문과 어긋나면 회의가 이긴다** `[설계: 원문은 신청 시점의 계획이고 회의는 그 뒤의 결정이다]`. 다만 **어긋난다는 사실을 지우지 않는다** — 어느 쪽을 따랐는지 나중에 확인할 수 있어야 한다. 어긋나는 경우 **양쪽을 함께 적는다.**

세부 규칙:

1. `[원문 …]`의 페이지는 **PDF 파일 페이지 번호**다(인쇄 쪽번호와 다름). 표기 형식은 셋뿐이다.

   | 쓸 때 | 형식 |
   |---|---|
   | 사업계획서 | `[원문 p.32]` · 여러 쪽은 `·`로 — `[원문 p.27·31]` |
   | 발표자료 | `[원문 발표 p.15]` — **`[발표 p.15]`로 줄이지 않는다** |
   | 두 원문 함께 | `[원문 p.65, 발표 p.16]` — 원문 사이는 `,`, 같은 원문의 쪽 사이는 `·` |

2. `[PROVISIONAL]` 값은 반드시 [`src/shared/config/provisional.ts`](../../src/shared/config/provisional.ts) **한 파일에만** 실체가 있다. 문서는 그 값을 인용만 한다.
3. `[TBD-nn]`·`[INC-nn]` 번호는 [`source-inconsistencies.md`](../requirements/source-inconsistencies.md)에 등록된 것만 쓴다. 새 항목이면 거기 먼저 등록한다. **번호를 붙이기 전에 그 항목의 실제 등록 내용을 읽는다** — 뜻이 다른 번호를 붙이면 근거가 있다는 착각만 남는다.
4. `[설계]`에는 **기각한 대안**을 함께 적으면 더 좋다. 나중에 같은 검토를 반복하지 않는다.
5. **원문이 확정하지 않은 것을 확정된 사실처럼 쓰지 않는다.** "센서가 없다"가 아니라 "추정으로 다뤘다 + 센서 유무는 `[TBD-nn]`"이다. 우리가 고른 쪽과 원문이 정한 것은 다르다.
6. **원문이 목록으로 제시한 것은 전수를 대조한다.** 일부만 쓰더라도 **나머지를 "왜 안 쓰는지"와 함께 적는다.** 세지 않으면 빠진 줄 모른다.

> 규칙 6이 왜 필요한가 — 실제로 두 번 놓쳤다.
>
> | 원문 목록 | 놓친 것 |
> |---|---|
> | 수요처 6종 `[원문 p.1]` | 4종만 근거를 확인했고, 나머지 2종에 사용 방식 서술이 없다는 사실을 몰랐다 → `[TBD-40]` |
> | 필요 데이터 4그룹 `[원문 p.1]` | 5개 항목(수위·방류 여부·설비 ON/OFF·배출주기·공정 운영 정보)을 언급조차 안 해, **없는 데이터처럼 읽혔다** → [`data-definition.md` §4.1](data-definition.md) |
>
> 둘 다 **필요한 것만 집어 쓰고 세지 않아서** 생겼다. 목록을 만나면 먼저 개수를 세고, 쓰지 않는 항목에 이유를 붙인다.

> 이 규약을 지키면 "근거가 뭐냐"는 질문에 문서 한 줄로 답할 수 있다. 지키지 않으면 다시 코드를 열어야 한다.

### 3.3 태그 검증

번호를 잘못 붙여도 문서는 멀쩡해 보인다. 세어서 확인한다.

```bash
npm run verify:docs
```

[`scripts/verify-docs.mjs`](../../scripts/verify-docs.mjs)가 **13종**을 검사한다. 실패하면 exit 1이다. 종수는 `results.length`로 자동 계산되므로 검사를 더하면 출력이 따라 바뀐다.

| # | 검사 | 무엇을 막는가 |
|---|---|---|
| 1 | 태그 등록 | 등록되지 않은 `[TBD-nn]`·`[INC-nn]` (`·` 축약 전개) |
| 2 | 인용 형식 | `[발표 p.nn]` 축약형 |
| 3 | 화면 수 | 목록·문서·라우트가 갈리는 것 |
| 4 | FR 커버리지 | FR-01~42 누락 |
| 5 | 문서 링크 | 깨진 상대 링크 — `docs/` · `CLAUDE.md` · `.claude/rules/` |
| 6 | 필드 커버리지 | 타입에 필드를 더하고 문서를 안 고치는 것 |
| 7 | 문서 규격 | 문서정보 4필드·변경 이력 누락 |
| 8 | 화면 목록 정합 | `screens.md`와 화면 문서가 다른 말을 하는 것 |
| 9 | 자릿수 하드코딩 | 같은 값이 화면마다 다르게 반올림되는 것 — `toFixed(1)`·`decimals={1}`·`decimals: 1` (**E1**) |
| 10 | 임시값 위치 | `PROVISIONAL_` 값이 `provisional.ts` 밖에 흩어지는 것 (§3 규칙 2) |

**검사를 여기 한 곳에만 둔다** `[설계: 검토할 때마다 손으로 스크립트를 짜면 회차마다 검사 항목이 달라져 매번 다른 것을 놓친다]`.

> **통과는 "형식이 어긋나지 않았다"는 뜻이지 "근거가 맞다"는 뜻이 아니다.**
> 태그 번호가 맞는 내용인지, 원문 페이지·수치가 맞는지는 **원문을 읽어야** 안다. 등록된 다른 항목의 번호를 붙이면 검사 1을 통과한다 — 그래서 §3 규칙 3이 "붙이기 전에 등록 내용을 읽는다"고 요구한다. 스크립트도 실행 말미에 이 한계를 찍는다.

## 4. ID 체계

xlsx 산출물이 **역할별 시트**로 나뉘므로 ID도 역할을 축으로 잡는다. 시트와 ID가 같은 축이라 변환할 때 섞이지 않는다.

### 4.1 화면 ID

```
SCR-<역할>-<일련번호 3자리>
```

| 역할 코드 | 대상 | 대응 xlsx 시트 |
|---|---|---|
| `AD` | 관리자 | 화면설계서 › 관리자용 |
| `OP` | 운영자 | 화면설계서 › 운영자용 |
| `GU` | 게스트 | 화면설계서 › 게스트용 |
| `CO` | **전 역할 공통** | 세 시트에 모두 등장 |

역할 코드는 **그 화면이 주로 속한 역할**을 뜻한다. 다른 역할의 접근 가능 여부는 화면 문서 §2의 권한 표(CRUD)가 따로 밝힌다.

`CO`는 **역할이 정해지기 전의 화면**이다 — 로그인이 그렇다. 로그인해야 역할이 생기므로 어느 역할 시트에도 속하지 않는다 `[설계: xlsx에 공통 시트가 없어 세 시트에 같은 행을 넣는다. 화면설계서 원본이 그렇게 쓰도록 만들어져 있다 — 운영자용·게스트용 시트에 같은 화면 ID가 들어간 예시 행이 있었다]`.

### 4.2 요구사항 ID

```
REQ-<구분>-<일련번호 3자리>
```

| 구분 코드 | 대상 | 대응 xlsx 시트 |
|---|---|---|
| `CO` | 시스템 공통 | 요구사항정의서 › 시스템 공통 |
| `AD` / `OP` / `GU` | 관리자 / 운영자 / 게스트 | 각 역할 시트 |
| `NF` | 비기능 | 요구사항정의서 › 비기능요구사항 |

### 4.3 원문 FR 번호와의 관계

원문 분석이 매긴 `FR-01`~`FR-42`는 **그대로 둔다.** `REQ-*`는 그것을 산출물 양식에 맞춰 다시 번호 매긴 것이며, [`requirements.md`](requirements.md)의 추적표가 둘을 잇는다.

```
FR-16 (원문 요구)  ↔  REQ-AD-014 (산출물 ID)  ↔  SCR-OP-006 (화면)  ↔  구현 상태
```

### 4.4 역할 모델 — 두 축으로 나눈다

역할 하나로 "무엇을 할 수 있는가"와 "무엇을 볼 수 있는가"를 동시에 표현할 수 없다. 원문도 둘을 따로 말한다.

| 축 | 근거 | 값 |
|---|---|---|
| **조작** 무엇을 할 수 있는가 | `[원문 p.69]` 접근제어(RBAC) | 관리자 · 운영자 · 게스트 |
| **범위** 무엇을 볼 수 있는가 | `[회의 2026-08-13]` (원문에는 없다 `[TBD-08]`) | 전 사업장 · 자사 1개소 |

**두 축이 곱해져야 실제 사용자가 된다.** 두 축은 **역상관**이다 — 넓게 보는 쪽이 얕게 조작하고, 깊게 조작하는 쪽이 좁게 본다.

| 실제 사용자 | 조작 | 범위 | 근거 |
|---|---|---|---|
| **통합 관제 주체** (B2B 본사 · B2B2C 대행업체 등) | 운영자 | **전 사업장** | `[회의 2026-08-13: 소규모 사업장 위에서 관리하는 주체가 있으며 모든 사업장을 통합 관제한다]` |
| **사업주 · 최고 책임자** (B2B 직접 수요처) | 관리자 | **자사 1개소** | `[회의 2026-08-13: 자사의 설비 제어·시스템 설정 등 모든 기능을 통제할 최종 권한]` · 개소당 손익 귀속 `[원문 p.40]` · 행정처분 리스크 `[원문 p.19]` |
| 지자체 · 단지 관리기관 · 환경공단 | 게스트 | 전 사업장 | **추측** — `[원문 p.69]` "조회만 가능" + FR-32·33 `[원문 p.33·42]` · `[원문 p.85·92]`. 회의에서 정해지지 않았다 |

> **원문과 어긋나는 부분** — `[원문 p.50]`은 Application Layer를 "현장 운영자 중심 설계"라 하고 운영 인력을 개소당 0.5~1명으로 잡아 `[원문 발표 p.49]`, **운영자를 사업장 안의 사람으로 읽히게 한다.** 회의는 운영자를 **사업장 위의 통합 관제 주체**로 정했다. 규약대로 **회의가 이긴다.**
>
> 다만 p.50이 말한 "현장 운영자"의 실태(겸직 70%·AI 이해도 부족)는 여전히 유효하다 — 그 사람은 이제 **관리자** 쪽에 속한다. 아래 "주 사용자는 전문가가 아니다"를 관리자 화면 설계에 적용한다.

#### 주 사용자는 전문가가 아니다 — 화면 설계의 전제

원문은 **화면이 누구를 위한 것인지**를 구체적으로 말한다. 전문을 [`functional-requirements.md` §3.3.1](../requirements/functional-requirements.md)에 옮겼다.

| 사실 | 근거 |
|---|---|
| 중소 사업장 **약 70%가 환경관리 전담 인력 없이 겸직**(생산관리자·시설관리자) | `[원문 p.19·20]` |
| **전문 지식 부족**으로 데이터 해석·이상 징후 판단·조치 수립이 어렵다 | `[원문 p.20]` |
| 사고의 **60%가 비근무 시간대** — 야간 35%(무인 운전 중) · 주말 25%(관리 인력 부재) | `[원문 p.19]` |
| 이상 발생 시 **경험 기반 원인 추정에 의존** — "TOC가 상승했는데 펌프 이상인지 유입 부하 증가인지 판단 어려움" | `[원문 p.22]` |
| SWOT 약점 — 현장 운영자의 **AI 활용 역량 부족** | `[원문 p.83]` |
| 위험 대응 — 문제는 "**AI 이해도 부족**", 대응책은 **자동 의사결정 가이드**·**알림 기반 단순화된 운영 방식** | `[원문 p.94]` |

**따라서 역할 설계의 방향은 권한을 좁히는 것이 아니라 판단을 대신해 주는 것이다** `[설계: 원문이 대응책으로 든 것이 권한 분리가 아니라 "자동 의사결정 가이드"와 "알림 기반 단순화"다. 겸직·비전문가에게 해석 부담을 넘기는 화면은 원문의 문제 정의를 거스른다]`.

역할별 화면(`SCR-AD-*`·`SCR-OP-*`·`SCR-GU-*`)이 지킬 것 — **특히 관리자 화면이다.** 위에서 본 대로 원문이 말한 '현장 운영자'는 회의 이후 관리자 쪽 사람이 되었다:

| 원칙 | 이유 |
|---|---|
| **무엇을 해야 하는지**를 값과 함께 낸다 | 값만 주면 경험 기반 추정으로 되돌아간다 `[원문 p.22]` |
| AI 산출값에 **근거를 반드시 병기**한다(**E3**) | "이해하고 신뢰할 수 있어야 실제 의사결정에 활용 가능" `[원문 p.59]` |
| 알람에서 **바로 판단 가능**해야 한다 | 사고의 60%가 사람이 없는 시간에 일어난다 `[원문 p.19]` |
| 전문 용어를 값 옆에 풀어 쓴다 | 전담 인력이 아니라 겸직자가 본다 `[원문 p.19·20]` |

#### 조작 축이 화면 ID를 정한다

화면 ID 접두사(`SCR-AD/OP/GU`)는 **조작 축**을 따른다 — xlsx가 역할별 시트로 나뉜 축과 같다. 범위 축은 화면을 나누지 않고 **같은 화면이 보여 주는 사업장 집합**만 바꾼다.

#### 범위 축 — 정해진 것과 아직 아닌 것을 나눈다

**역할별 범위는 정해졌다** `[회의 2026-08-13]` — 운영자·게스트는 전 사업장, 관리자는 자사 1개소다. 이것은 위 표대로 화면에 구현되어 있다.

**아직 정해지지 않은 것은 계정↔사업장 매핑이다** `[TBD-08]`(사업장 단위 데이터 접근 범위)·`[TBD-11]`(요금제별 관리 범위). *어느* 계정이 *어느* 사업장의 사업주인지는 계약 구조가 정해져야 확정된다.

프로토타입은 그 자리를 **관리자 계정 2종**으로 메운다 `[설계: 확정되지 않은 것은 매핑이지 범위가 아니다. 매핑을 시연값으로 두면 범위 규칙은 지금 확인할 수 있고, 확정 시 계정 배열 한 곳만 고치면 된다]` — 실체는 [`entities/user/config/accounts.ts`](../../src/entities/user/config/accounts.ts) 한 파일에 있다.

| 계정 | 사업장 | 고른 이유 |
|---|---|---|
| 관리자1 | 구미 염색 2공장 (S-02) | 이상 88 위험 · 미확인 알람 2건 — 값이 가득한 화면 |
| 관리자2 | 수원 전자부품 세정 (S-09) | 이상 14 정상 · 알람 0건 — **빈 상태 처리**를 함께 확인 |

**전 사업장을 보여주던 이전 결정은 이 결정으로 대체됐다.** 그때는 역할별 범위 자체가 미확정이라 "임의로 좁히면 계약 구조를 사실로 굳힌다"는 이유였는데, 회의가 범위를 정하면서 그 전제가 사라졌다.

> 이 분기는 **인가가 아니라 시연용 표시**다(`frontend.rule.md` **E6** 예외). 서버가 없어 클라이언트 역할 전환일 뿐이며, 백엔드 착수 시 서버 응답 권한으로 교체한다.

## 6. 공통 설계 규약

### 6.1 URL이 화면 상태를 가진다

`frontend.rule.md` **P6**에 따라 사업장·기간·항목 필터를 URL 쿼리에 둔다 `[설계: 링크를 그대로 공유하면 같은 화면이 열리고, 화면을 옮겨도 선택이 유지된다]`.

| 키 | 값 | 사용 화면 | 기본값 |
|---|---|---|---|
| `site` | 사업장 id | 전 화면 | `DEFAULT_SITE_ID` |
| `hours` | `6` \| `12` \| `24` | SCR-OP-003, SCR-OP-008 | `24` |
| `cat` | `water` \| `equipment` \| `all` | SCR-OP-003 | `water` |
| `target` | `TOC` \| `TN` \| `TP` | SCR-OP-004 | `TOC` |
| `sort` | `mpi` \| `failure` \| `rul` | SCR-OP-005 | `mpi` |
| `prio` | `all` \| `urgent` \| `caution` \| `info` | SCR-OP-007 | `all` |
| `state` | `all` \| `open` \| `acknowledged` \| `resolved` | SCR-OP-007 | `all` |
| `scope` | `all` \| `site` | SCR-OP-007 | `all` |

허용 목록에 없는 값이 들어오면 빈 화면 대신 기본값으로 되돌린다([`shared/lib/use-query-state.ts`](../../src/shared/lib/use-query-state.ts)).

> 이 때문에 전 라우트가 동적 렌더(`ƒ Dynamic`)다. 정적 프리렌더는 쿼리를 모르므로 사이드바가 스켈레톤으로 굳는다. 실시간 관제 화면이라 손해가 없다.

### 6.2 모든 화면이 지키는 도메인 규칙

`frontend.rule.md` §8.1의 E1~E6이다. 화면 문서마다 다시 설명하지 않고 여기를 가리킨다.

| # | 규칙 |
|---|---|
| **E1** | 계측값의 단위·소수 자릿수는 항목별로 한 곳에서만 정한다. 화면마다 다르게 반올림하지 않는다 |
| **E2** | 상태 등급은 잠정 4단계 `정상/주의/경고/위험` `[INC-01·03·04]`. 화면별 추가·병합 금지 |
| **E3** | AI 산출값에는 **산출 시각·대상 기간·모델**을 함께 낸다. 값이 없으면 빈 상태로 둔다 |
| **E4** | 결측·통신두절을 **0으로 채우지 않는다.** 끊긴 구간으로 표현한다 |
| **E5** | 시각에 기준 시간대(KST)를 명시하고 수집 주기·조회 기간을 함께 드러낸다 |
| **E6** | 권한 노출은 서버 응답이 근거. **현 단계 예외** — 서버가 없어 mock 역할 전환이며 인가가 아니라 시연 표시다 |

### 6.3 데이터 원천

현재 데이터는 전부 fixture다. 원천은 [`src/shared/config/demo-scenario.ts`](../../src/shared/config/demo-scenario.ts) **한 곳**이며, 각 슬라이스가 여기서 자기 몫만 읽어 생성한다 `[설계: 슬라이스끼리 참조하지 않으면서(FSD §8) 값이 구조적으로 일치하게 하려고]`.

## 7. 백엔드 착수 시 확인할 것

화면이 이미 전제하고 있는 것들이다. 계약 설계 때 어긋나면 화면을 고쳐야 한다.

1. **결측 표현** — 화면은 `null`을 기대한다. `0`이나 `-999` 같은 센티널로 내려오면 **E4를 지킬 수 없다.**
2. **AI 산출값의 메타데이터** — 값만 주면 안 된다. 산출 시각·대상 기간·모델이 함께 와야 **E3**를 지킨다.
3. **등급 판정 위치** — 점수→등급 변환을 서버가 할지 클라이언트가 할지. 현재는 클라이언트([`toStatusLevel`](../../src/shared/config/provisional.ts)).
4. **권한** — 현재 역할 분기는 인가가 아니라 시연 표시다(**E6 예외**). 서버 응답 권한으로 교체해야 한다.
5. **시간대** — 현재 포맷터는 시연 데이터가 KST 벽시계라는 전제에 기대고 있다. 실제 타임스탬프가 들어오면 시간대 변환을 제대로 해야 한다.
6. **신뢰구간의 신뢰수준** — 원문에 없다(95%? 90%?). 현재는 시간에 비례해 벌어지는 폭으로만 그린다.

## 9. 화면 문서 템플릿

새 화면 문서는 아래를 복사해 쓴다. 섹션을 생략하거나 순서를 바꾸지 않는다 — **비어 있으면 "해당 없음"이라고 적는다.** 빈 섹션은 "아직 안 정했다"와 "정할 것이 없다"를 구분해 준다.

```markdown
# 화면 설계 — {화면명} ({화면ID})

## 1. 문서 정보
   (document-template.rule.md 규격: 문서명·버전·작성일·기반 문서 + 변경 이력)

## 2. 화면 개요
   | 화면 ID | 메뉴(1Depth) | 메뉴(2Depth) | 화면 구분 | 경로 | 구현 파일 |
   | 관련 요구사항 |
   | 권한 CRUD — 관리자 / 운영자 / 게스트 |

## 3. 화면 구성
   레이아웃 도식 + 구성요소·형태 표 (→ 화면설계서 K·L열)

## 4. 요구 데이터
   | 데이터 | 타입 | 단위 | 출처·근거 표기 | UI 위치 |
   (→ data-definition.md로 승계)

## 5. 상호작용
   | 조작 | 동작 | 결과(After Action) |
   SUBMIT / CANCEL 해당 여부 (→ 화면설계서 M·N·O열)

## 6. 상태와 예외
   로딩 · 빈 상태 · 통신두절 · 결측 · 권한 없음

## 7. 설계 근거
   왜 이 구성인가. 검토했다 기각한 대안과 이유.
   시각(색·타이포) 근거는 design-system 문서를 링크로 가리킨다.

## 8. 미정·제약
   | 항목 | 표기 | 확정 필요 시점 |
```
