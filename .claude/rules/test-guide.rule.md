## 2. 기본 원칙

- **구현 후 테스트 필수**: 기능/버그 수정 후 의도대로 동작하는지 검증한다.
- **테스트 우선 지향**: 구현과 동시 또는 직후 단위 테스트 작성.
- **실패 케이스 포함**: 성공 시나리오뿐 아니라 예외(빈 값·null·경계·네트워크 실패·통신 두절)를 설계에 포함.

## 4. 체크리스트

### 4.1 정적 분석
- [ ] 구문 오류·미정의 참조 없음
- [ ] 린트/타입체크 통과

### 4.2 단위 테스트
- **독립성**: 외부 의존성은 목/스텁으로 격리(FE=MSW).
- **커버리지**: 핵심 비즈니스 로직 ≥ 80%.
- **명명**: `test_[대상]_[조건]_[기대결과]` 권장.

### 4.3 엣지 케이스
- [ ] null/undefined/빈 문자열/0/빈 배열 처리
- [ ] 인덱스 경계
- [ ] 네트워크 지연·API 실패 시 에러 핸들링(빈 상태/스켈레톤/재시도)
- [ ] 계측 데이터 결측·통신 두절 구간(0으로 대체하지 않고 끊긴 구간으로 표현)
- [ ] 센서 미설치·미지원 항목, 신규 사업장(데이터 0건)

## 5. 도메인별 필수 검증(요약)

- **인증/권한**: RBAC(관리자/운영자/게스트) 인가 우회 0건(서버 강제), 토큰 만료/재발급. 권한 없는 기능이 UI에 노출되지 않는지 검증.
- **실시간 계측 모니터링**: 수집 주기(1~10분) 갱신 동작, 값·단위·소수 자릿수 표시 규칙, 시간대 표기, 지연·재연결 처리.
- **이상탐지·알람**: 이상 점수(0~100) 경계값 분기, 알람 우선순위(긴급/주의/정보) 표기, 알람 목록·확인/조치 상태 전이, 중복 알람 처리. 상태 등급 체계는 확정 후 경계값 테스트를 추가한다(→ `docs/requirements/source-inconsistencies.md`).
- **예측·오염도 추정**: 예측 구간(1~6시간) 표시, 경향(상승/유지/하락) 매핑, 산출 시각·대상 기간 노출, 값 없음 상태.
- **설비 예지보전**: 설비 상태 등급 표기, 유지관리 우선순위 정렬 기준.
- **시계열 성능**: 장기간·다항목 조회 시 렌더 지연·프리즈 없는지 확인(기준 수치는 [TBD], 확정 전 회귀 비교로 판단).

## 6. 응답 전략(구현 요청 시)
1. 코드 구현 → 2. 테스트 계획 요약 → 3. 테스트 코드 작성 → 4. 실행 결과(PASS) 또는 논리적 결함 없음 증명.

## 7. 회귀
- 신규 기능 추가 시 기존 테스트가 깨지지 않는지 확인. 기존 기능 수정 시 영향 모듈 테스트도 갱신.
- 테스트를 통과하지 못한 코드는 '완성'으로 간주하지 않는다.
